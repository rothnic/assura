Assura tracks performance evidence as machine-readable JSON so release notes,
pull requests, and this website all point at the same data contract.

## Current Data

- [Current comparison report](/data/performance/current.json)
- [Chart-ready JSONL history](/data/performance/ls-lint-comparison-history.jsonl)
- [Tracked schema](https://github.com/rothnic/assura/blob/master/benches/history/ls-lint-comparison.schema.json)

The comparison covers stable fixture cohorts for small, medium, large,
rule-heavy, ignored/generated-heavy, library, web app, and monorepo project
shapes. Rows include schema version, timestamp, commit, branch, OS,
architecture, Rust version, Node/npm versions, tool version, fixture metadata,
rule cohort, tool name, median runtime, sample distribution, pass/fail status,
and baseline identifier. The same report also includes traversal-only rows
named `walkdir`, `jwalk-serial`, and `jwalk-parallel` so PRs can compare the
production traversal strategy beside the LS-Lint parity comparison.

Assura rows also include per-fixture phase timings:
`assura:config-discovery`, `assura:config-load`, `assura:checker-init`,
`assura:configured-structure`, `assura:walk-and-validate`, and
`assura:report-sort`. These rows are intended to make hotspot claims
reviewable without scraping local Criterion output.

## Baseline Table

The current realistic equivalent fixtures show Assura multiple times faster
than warm LS-Lint 2.3 on the same generated project shapes:

- `simple_library` (`realistic-library`): Assura 0.843 ms; LS-Lint 104.185
  ms; **123.5x faster**.
- `web_app` (`realistic-frontend`): Assura 0.801 ms; LS-Lint 101.060 ms;
  **126.2x faster**.
- `monorepo_packages` (`realistic-monorepo`): Assura 1.669 ms; LS-Lint
  104.973 ms; **62.9x faster**.
- `rule_heavy_repo` (`realistic-multi-extension-patterns`): Assura 26.145 ms;
  LS-Lint 99.177 ms; **3.8x faster**.
- `ignored_generated_heavy_repo` (`realistic-exclude-pruning`): Assura 0.542
  ms; LS-Lint 108.457 ms; **200.3x faster**.

Synthetic and scale-stress fixtures are tracked separately. They are useful for
finding bottlenecks, but they are not the basis for the realistic-equivalent
"multiple times faster" claim:

- `simple_small` (`extension-dir-naming`): Assura 1.762 ms; LS-Lint 106.812
  ms. Synthetic small baseline.
- `simple_medium` (`extension-dir-naming`): Assura 23.810 ms; LS-Lint 112.705
  ms. Synthetic medium baseline.
- `monorepo_large` (`extension-dir-naming`): Assura 110.748 ms; LS-Lint
  133.766 ms. Synthetic large baseline.
- `rule_heavy` (`multi-extension-patterns`): Assura 173.930 ms; LS-Lint
  117.829 ms. Synthetic stress case where LS-Lint is faster.
- `ignored_generated_heavy` (`exclude-pruning`): Assura 0.509 ms; LS-Lint
  102.912 ms. Synthetic generated-output pruning case.

Pull requests attach a `ls-lint-performance-report` artifact and write a
summary table to the GitHub Actions job summary. The summary includes both
Assura versus LS-Lint fixture timings and traversal timings for `walkdir`,
serial `jwalk`, and parallel `jwalk`. The summary also includes a phase
breakdown table for each fixture. CI does not update tracked history
automatically.

## Interpreting The Rows

Traversal rows are intentionally narrower than top-level Assura rows.
`walkdir`, `jwalk-serial`, and `jwalk-parallel` measure raw entry enumeration.
They do not include config loading, effective rule resolution, naming-pattern
validation, file-content reads, markdown checks, or report sorting.

Use top-level `assura` rows for product comparisons. Use traversal rows only to
understand whether traversal itself is a hotspot.

`rule_heavy` and `rule_heavy_repo` are different fixtures:

- `rule_heavy` is a synthetic stress fixture with many files and many
  extension-specific rules.
- `rule_heavy_repo` is a smaller repo-shaped fixture that exercises similar
  multi-extension rules under a more realistic directory shape.

LS-Lint rows use a prepared `@ls-lint/ls-lint@2.3.0` binary. They avoid
repeated npm package resolution, but they still include process startup,
LS-Lint config loading, traversal, and validation for each sample.

The full interpretation for PR #11 is tracked in
[`docs/analysis/2026-05-16-performance-results-interpretation.md`](https://github.com/rothnic/assura/blob/master/docs/analysis/2026-05-16-performance-results-interpretation.md).

## Updating The Baseline

Baseline updates are explicit source changes:

```bash
cargo run --quiet -- performance-report \
  --output benches/history/current.json \
  --history benches/history/ls-lint-comparison-history.jsonl \
  --website-dir website/public/data/performance \
  --iterations 5
```

Review the generated diff in `benches/history/` and
`website/public/data/performance/` before merging. If LS-Lint cannot be fetched
or executed, the report keeps Assura rows and marks LS-Lint rows as `skipped`
with the exact blocker in `details`.
