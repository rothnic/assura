## What Was Compared

marked native LS-Lint parity. Each fixture is generated once, writes a
`.ls-lint.yml`, converts that same LS-Lint-compatible config into
`.assura/config.yml`, then runs both tools against the same fixture directory.

The table shows source-tree shape, rule surface, and timing in one place so the
comparison can be reviewed as an apples-to-apples claim instead of a raw speed
claim.

## Fairness Contract

The current comparison is fair for native LS-Lint parity rows under these
constraints:

- The fixture manifest records fixture purpose, LS-Lint rule surface, equivalent
  Assura rule surface, parity status, and source revision.
- `write_lslint_compatible_configs` converts the LS-Lint-compatible config into
  Assura config, then writes both configs into the same generated fixture tree.
- LS-Lint uses a prepared `@ls-lint/ls-lint@2.3.0` binary. The measured loop
  still includes process startup, LS-Lint config loading, traversal, and
  validation, so these are warm CLI execution timings rather than in-process
  library timings.
- Assura top-level rows include config discovery/load, checker initialization,
  configured structure validation, walking and validation, and report sorting.

This page does not claim that Assura is faster for every possible LS-Lint
configuration. It claims that Assura is faster on the current native-parity
realistic bundle, and it shows the fixture shape needed to judge whether that
bundle is representative.

## Interpreting Traversal Rows

Traversal rows are intentionally narrower than top-level Assura rows.
`walkdir`, `jwalk-serial`, and `jwalk-parallel` measure raw entry enumeration.
They do not include config loading, effective rule resolution, naming-pattern
validation, file-content reads, markdown checks, or report sorting.

Use top-level `assura` rows for product comparisons. Use traversal rows only to
understand whether traversal itself is a hotspot. Before changing the production
traversal default again, the report should add full-check strategy rows that
compare walkdir, serial `jwalk`, and parallel `jwalk` under the same validation
logic.

## Updating The Baseline

Baseline updates are explicit source changes:

```bash
cargo run --quiet -- performance-report \
  --output benches/history/current.json \
  --history benches/history/ls-lint-comparison-history.jsonl \
  --website-dir website/public/data/performance \
  --iterations 5
```

Review the generated diff in `benches/history/` and
`website/public/data/performance/` before merging. If LS-Lint cannot be fetched
or executed, the report keeps Assura rows and marks LS-Lint rows as `skipped`
with the exact blocker in `details`.
