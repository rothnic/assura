# Repo-Native Content Runtime Implementation

## Objective

Bring the repo-native content object prototype into a production-oriented
Assura implementation branch and PR.

The implementation should let Assura load a checked-in runtime schema artifact,
discover configured content collections, parse file-backed records, validate
shape and references natively in Rust, and expose one typed agent mutation
operation without requiring any authoring toolchain in the hot path.

## Current Gap

The current branch proves the architecture with fixtures and integration tests,
but it is still prototype evidence:

- runtime schemas are manual normalized snapshots, not generated by a compiler;
- the JSON Schema validator is currently dev-only proof dependency;
- adapters and relation checks live in test code, not production modules;
- there is no public config entry for models or content collections;
- there is no CLI/API surface for agent operations;
- Deeb has been evaluated conceptually, but not benchmarked as an optional
  cache/index backend.

## User Certainty Bar

Users should be able to inspect a normal repo and understand:

- which object classes can live under which paths;
- which file adapter handles each collection;
- which runtime schema artifact validates each class;
- which references are required or optional;
- which typed operation an agent should call to create or update a record.

They should not need to understand LinkML, TypeSpec, Rust derive macros, Deeb,
or a server to run validation.

## Scope

Implement the smallest production slice:

- config support for a `models:` or equivalent content-object runtime block;
- runtime artifact loading from JSON Schema-like files;
- compiled/cached Rust validators;
- collection discovery for at least:
  - Markdown frontmatter records;
  - JSON records;
- stable object identity from configured `id` fields;
- source path metadata for diagnostics;
- cross-collection reference validation;
- one typed agent operation contract, preferably `create_record` or
  `create_task`, with validation before write;
- focused docs explaining that LinkML is authoring-time only and JSON Schema is
  runtime.

Stretch only after the vertical slice is green:

- YAML record adapter;
- JSONL record adapter;
- LinkML profile generation command;
- Deeb or file-index benchmark as an optional cache comparison.

## Non-Goals

- Do not implement a CMS UI.
- Do not require a running server.
- Do not make Deeb, SQLite, or another database canonical source of truth.
- Do not require LinkML, TypeSpec, Node, Python, Go, or CUE for normal
  validation.
- Do not create a new Assura schema DSL unless the LinkML profile and TypeSpec
  decorator paths are explicitly rejected with evidence.
- Do not migrate all existing Assura config notation in this goal.

## Definition Of Done

- A new implementation branch is created from the current base after the
  prototype PR is reviewed or merged.
- A production module loads runtime schema artifacts and caches validators.
- Config can bind classes to collection paths and adapters.
- Markdown frontmatter and JSON records validate as logical objects.
- Missing references across collections produce clear diagnostics with source
  paths.
- One typed agent operation validates its payload and writes a record only after
  shape and reference checks pass.
- Docs include the decision and user-facing path:
  LinkML profile first, TypeSpec fallback, JSON Schema runtime, Assura-owned
  adapters/relations/writes.
- Review evidence is captured before opening or marking the PR ready.
- A PR is opened with a summary, validation commands, reviewer findings, and
  remaining risks.

## Validation Commands

Minimum local validation:

```bash
python3 ./.trellis/scripts/workflow_gate.py --platform codex
cargo fmt --check
cargo test --test artifact_authoring_paths_proof --quiet
cargo test --test artifact_modeling_options_comparison --quiet
cargo test --workspace --all-targets --all-features
cargo run --quiet -- check --format json .
cargo xtask evidence
cargo xtask docs
git diff --check
```

If the implementation changes CLI behavior, add:

```bash
cargo run --quiet -- check --format json tests/fixtures/<new-content-runtime-fixture>
```

## Review Tasks

Use at least one review agent before opening or marking the PR ready.

Reviewer blocking criteria:

- Block if runtime validation shells out to LinkML, TypeSpec, Node, Python, Go,
  CUE, Deeb, SQLite, or a server.
- Block if the public config makes Rust structs, Rust derive macros, or Cargo
  build steps the model source for non-Rust projects.
- Block if reference validation is omitted or only validates field shape.
- Block if safe writes can partially update files after validation failure.
- Block if Markdown body bytes are changed by a frontmatter-only operation.
- Block if diagnostics do not identify the source file and field.
- Block if test fixtures do not include both passing and failing cases.

## PR Plan

1. Publish the current prototype branch as a PR titled:
   `Research repo-native content object runtime`.
2. Ask the reviewer to focus on whether the decision and next goal are
   sufficiently concrete.
3. After review, create a fresh implementation branch from the reviewed base:
   `codex/repo-native-content-runtime-implementation`.
4. Implement the vertical slice above.
5. Open a second PR for implementation once validation and review pass.

## Expected Outcome

The implementation PR should make Assura responsible for the runtime object
model and file operations while keeping authoring tools optional. LinkML should
improve the model authoring story, not become a runtime dependency. TypeSpec
should remain a fallback path until the decorator package is tested. Deeb
should remain a possible internal cache/index experiment, not the public model
source.
