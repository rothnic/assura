# Repo-Native Content Runtime Implementation

## Objective

Bring the repo-native content object prototype into a production-oriented
Assura implementation program, starting with the first runtime slice and then
continuing through the remaining increments required for a complete, usable
feature.

Complete means Assura can:

- load checked-in runtime schema artifacts;
- discover configured content collections;
- parse file-backed records as logical objects;
- validate shape and references natively in Rust;
- expose safe typed agent mutations for create and update workflows;
- support Markdown frontmatter, JSON, YAML, and JSONL-backed collections;
- use LinkML or another authoring tool only to generate runtime artifacts;
- provide docs and examples that make the model inspectable by TypeScript,
  Python, and Rust users without requiring a running server.

## Current Gap

The current branch proves the architecture with fixtures and integration tests,
but it is still prototype evidence:

- runtime schemas are manual normalized snapshots, not generated by a compiler;
- the JSON Schema validator is currently dev-only proof dependency;
- adapters and relation checks live in test code, not production modules;
- there is no public config entry for models or content collections;
- there is no CLI/API surface for agent operations;
- Deeb has been evaluated conceptually, but not benchmarked as an optional
  cache/index backend.

## User Certainty Bar

Users should be able to inspect a normal repo and understand:

- which object classes can live under which paths;
- which file adapter handles each collection;
- which runtime schema artifact validates each class;
- which references are required or optional;
- which typed operation an agent should call to create or update a record.

They should not need to understand LinkML, TypeSpec, Rust derive macros, Deeb,
or a server to run validation.

## Completion Definition

The end solution is not just a proof that validation can work. It is complete
when a repo can define its own typed artifacts, store them in ordinary files,
validate them with `assura check`, and let an agent perform bounded write
operations through an Assura-owned contract.

A complete result must prove:

- project config can say which object types may live under which paths;
- each collection declares its storage adapter, schema artifact, ID field, and
  reference fields;
- shape validation uses compiled or cached Rust validators in the runtime path;
- reference validation resolves records across collections and reports source
  file plus field;
- typed mutations validate the payload and affected references before writing;
- Markdown frontmatter writes preserve the Markdown body bytes;
- JSON, YAML, and JSONL writes are deterministic and atomic;
- authoring formats such as LinkML are optional build-time inputs, not runtime
  dependencies;
- docs and examples demonstrate the same model in Markdown frontmatter and JSON
  form;
- developer experience evidence shows the model can be inspected with ordinary
  editor and language tooling, especially JSON Schema-aware tooling;
- performance evidence shows validation remains appropriate for normal
  `assura check` use.

review stays clear. The first implementation PR may cover increments 0 and 1

## First Slice Scope

Start with increment 1 after increment 0 is clean. The first production slice
must include:

- config support for a `models:` or equivalent content-object runtime block;
- runtime artifact loading from JSON Schema-like files;
- compiled or cached Rust validators;
- collection discovery for Markdown frontmatter records and JSON records;
- stable object identity from configured `id` fields;
- source path metadata for diagnostics;
- cross-collection reference validation;
- focused docs explaining that authoring tools are optional and runtime
  validation is Rust-native.

The first slice does not need write operations, YAML, JSONL, LinkML generation,
or Deeb benchmarking, but it must leave clear extension points for each later
increment.

## Non-Goals

- Do not implement a CMS UI.
- Do not require a running server.
- Do not make Deeb, SQLite, or another database canonical source of truth.
- Do not require LinkML, TypeSpec, Node, Python, Go, or CUE for normal
  validation.
- Do not create a new Assura schema DSL unless the authoring-tool decision
  rejects existing practical options with evidence.
- Do not migrate all existing Assura config notation in this goal.

## Program Definition Of Done

- A new implementation branch is created from a reviewed base after prototype
  artifacts are either merged intentionally or parked.
- Each increment above has a PR, review notes, and validation evidence, or an
  explicit note explaining why it was combined with another increment.
- Production modules load runtime schema artifacts and cache validators.
- Config can bind object classes to collection paths, adapters, ID fields, and
  reference fields.
- Markdown frontmatter, JSON, YAML, and JSONL records validate as logical
  objects.
- Missing references across collections produce clear diagnostics with source
  paths and fields.
- Typed create and update operations validate payloads and references before
  writing.
- Safe-write tests prove failed validation leaves the working tree unchanged.
- Docs include the decision and user-facing path:
  selected authoring profile, JSON Schema-compatible runtime artifacts, and
  Assura-owned adapters/relations/writes.
- DX evidence covers at least TypeScript, Python, and Rust inspection paths.
- Performance evidence is captured before release readiness is claimed.
- Review evidence is captured before opening or marking each PR ready.
- The final PR summary maps completed work back to every increment in this
  goal.

## Validation Commands

Minimum validation for each PR starts with the workflow and repository checks:

```bash
python3 ./.trellis/scripts/workflow_gate.py --platform codex
cargo fmt --check
cargo test --workspace --all-targets --all-features
cargo run --quiet -- check --format json .
cargo xtask evidence
cargo xtask docs
git diff --check
```

As the named increment tests are added, include the available subset. By release
readiness, all of these test targets should exist and pass:

```bash
cargo test --test content_runtime_validation --quiet
cargo test --test content_runtime_create --quiet
cargo test --test content_runtime_update --quiet
cargo test --test content_runtime_references --quiet
```

If the implementation changes CLI behavior, add:

```bash
cargo run --quiet -- check --format json tests/fixtures/<new-content-runtime-fixture>
```

## Review Tasks

Use at least one review agent before opening or marking the PR ready.

Reviewer blocking criteria:

- Block if runtime validation shells out to LinkML, TypeSpec, Node, Python, Go,
  CUE, Deeb, SQLite, or a server.
- Block if the public config makes Rust structs, Rust derive macros, or Cargo
  build steps the model source for non-Rust projects.
- Block if reference validation is omitted or only validates field shape.
- Block if safe writes can partially update files after validation failure.
- Block if Markdown body bytes are changed by a frontmatter-only operation.
- Block if diagnostics do not identify the source file and field.
- Block if test fixtures do not include both passing and failing cases.

## PR Plan

1. Publish the current prototype branch as a PR titled:
   `Research repo-native content object runtime`.
2. Ask the reviewer to focus on whether the decision and next goal are
   sufficiently concrete.
3. Park or merge only the research artifacts needed for implementation. Do not
   carry unused prototype-only code into the implementation branch.
4. After review, create a fresh implementation branch from the reviewed base:
   `codex/repo-native-content-runtime-implementation`.
5. Implement increments 0 and 1 first.
6. Open follow-up PRs for increments 2 through 11 until this goal's completion
   definition is satisfied.
7. Do not mark the goal complete after the first slice unless the remaining
   increments are split into successor goals with equivalent measurable gates.

## Expected Outcome

The implementation program should make Assura responsible for the runtime
object model and file operations while keeping authoring tools optional. LinkML,
TypeSpec, CUE, or a small Assura-owned profile may improve the model authoring
story, but none should become a runtime dependency unless this goal is
explicitly revised. Deeb should remain a possible internal cache/index
experiment, not the public model source.
